# Native PostgreSQL backup and restore

2026-10-03. Implementation and verification in progress. This document does not close Plan 029 or establish PostgreSQL parity. The preceding frozen source/package evidence remains unchanged.

The approved Backup/Restore Tool tab and table-context entry points are being connected to an app-owned observer. File selections, review tokens and session jobs are transient. Workspace format 5 stores only the tool tab identity and connection binding; it refuses job/path fields and preserves older supported workspace versions.

The native service registers a stable attempt before owned preparation. Restore preparation copies the inspected regular file into a private snapshot; inspection and execution use that snapshot. A review binds the backend owner, connection generation, exact intent and stored policy. Starting and confirming require explicit actions. An awaiting confirmation can be explicitly reviewed again after a lost token or pre-dispatch refusal, without executing or retrying the restore.

The service retains process, pipe, publication, source-copy and reaper joins under the shared shutdown deadlines. Missed deadlines and failed filesystem cleanup must remain failures with retained ownership. Restore dispatch retires old DataDocument handles and blocks new data handles until cleanup settles. SQL sessions and manual transactions remain separate. Successful and unknown restore outcomes advance a lifetime revision so released or expired history cannot conceal stale metadata or mutation sources.

The native observer outlives setup tabs, serializes commands and full-list observations, and never automatically retries a start. It reserves delivery allowance before dispatch. Retained setup, review, list and editor allocations use the existing shared payload allowance. Unknown restore outcomes require explicit target inspection and reconciliation before another setup can be prepared for that connection. Polling does not invent restore percentages.
