Plans 001 through 017 closed the daily-driver foundations. The next decision is among four real gaps, but one already has hidden backend work and an unsafe large-file boundary.

Recommendation
PAR-010: file-backed PostgreSQL backup and restore

Start with a dark backend plan. Existing native-tool commands capture full dumps in process memory, base64 them across IPC, and have no cancellation. Their former UI was deleted. Fixing that boundary before reactivation is the highest-leverage match for dbunk's reliability-first priority.

Proposed PAR-010 sequence

PLAN 018 · DARK BACKEND

File jobs and native-tool execution

  • Async pg_dump, psql, and pg_restore
  • Direct file paths, never dump bytes over IPC
  • Job IDs, progress phases, cancellation, deadlines
  • Tool/version preflight and typed errors
  • Partial-output and child-process cleanup
PLAN 019 · ACTIVATION

Reviewed backup and restore UI

  • Three static mocks before component work
  • PostgreSQL-only capability disclosure
  • Backup progress, cancel, success, and failure states
  • Restore preview and production confirmation
  • History without credentials or command-line secrets
PLAN 020 · TRANSFER

Bounded CSV import and export

  • Reuse the job/file lifecycle
  • PostgreSQL COPY TO/FROM with backpressure
  • Progress, cancellation, reject reporting
  • Explicit dialect, encoding, NULL, and transaction policy
  • Keep visible-row exports in memory

Plan 018 boundary

In

  • PostgreSQL native backup and restore only
  • Plain and custom dump formats
  • Existing TLS, tunnel, credential, and driver resolution
  • Backend safety policy for restore
  • Unit, process-fixture, and disposable PostgreSQL tests

Out

  • No production or daily-driver channel changes
  • No UI until Plan 019 and mock selection
  • No MySQL, SQLite, ClickHouse, or Redis backup parity
  • No scheduler or generalized task engine
  • No Parquet, XML, or generated database-DDL expansion
