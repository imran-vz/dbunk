# General native profile reconnaissance

Date: 2026-10-03. Source inspection only, after the formatter variant's 337-source-file freeze. No implementation, acceptance run, endpoint contact, profile opening, credential read, Keychain operation or UI interaction was performed. This note does not change plan status.

## Required boundary

[Plan030 sections 3–4](../../030-native-postgres-parity-acceptance.md) require a separate explicit native capability for user-selected PostgreSQL endpoints, with validated profile identity and scoped credentials. Fixture constructors and immutable manifests must retain their present meaning. An ordinary opener must not adopt an unmarked legacy database, convert a fixture profile, or select the Tauri daily-driver directory. Reopen restores disconnected state; Test and Connect are deliberate actions. Fresh profiles and a later copy-based importer must use the same service policy and lifecycle.

Production default paths, production Keychain/signature identity and copy-based migration remain separate work. Verification of general endpoint support is authorized only through newly created disposable profiles and explicitly owned test endpoints.

## Smallest implementation contract

1. Add separate `Backend::create_native_profile(path)` and `Backend::open_native_profile(path)` methods in a small new backend module. Creation requires a new canonical private directory. Opening requires an existing general marker and matching SQLite identity before migration or secret access. Suggested marker: `.dbunk-native-profile`; suggested setting: `native.profile.identity.v1`; fixed version/kind (`general-postgres`), exact canonical path and independent canonical UUIDv4 profile/credential identities. Bound the marker to 8 KiB, deny unknown fields, and refuse missing, corrupt, future, mixed or foreign markers without repair. Missing identities are errors, never instructions to generate replacements.
2. Give the existing internal authority an explicit endpoint capability, for example `OwnedFixtures(DevelopmentFixtures)` or `GeneralPostgres`. Only validated constructors create it. The fixture branch delegates to the existing exact `DevelopmentFixtures::permits` unchanged. General permits supported direct PostgreSQL records; it still rejects other engines, SSH and unreadable/unsupported connection options. Do not make absent fixtures mean general access. Keep stage03's existing `None` authority interpretation.
3. Centralize the authority's support decision and use it in both the connections facade and `admit_connection`. Continue reading stored metadata under the existing startup gate before credential hydration. Retain all generation, connection-policy, document ownership, recovery and shutdown checks. Reuse settings, journal, connections and data APIs; retain their existing public names for this increment if avoiding a broad compatibility rename.
4. Reuse the native credential lifecycle with a newly generated namespace. The minimum change can retain the existing opaque `dbunk-native-stage04-{UUID}` service format for general profiles: the unique validated UUID supplies isolation, not the word “stage04.” Document the expanded constructor use. If a separately named general service prefix is chosen, change the explicit store constructor and rollback-identity validator together, with injected-store tests; never change the prefix of an existing profile or fall back to legacy entries. This is not a production signing/identity decision.
5. Reuse the private path/file/lock primitives with only a narrow marker-name allowlist seam; keep stage04 `files::validate`, its exact allowed files, marker decoding and fixture validation intact. General validation has its own exact marker allowlist. Share the process-selected profile guard between stage04 and general mode. Do not infer a profile's capability from arbitrary files, a connection endpoint, missing CLI flags or a deserialized user request. Preserve the stage03 constructor; mutual-exclusive CLI selection must prevent host mode switching. If the public backend contract is intended to forbid mixed stage03/general constructors in one process too, that is an explicit additional guard change requiring separate tests, not an existing guarantee.
6. Add an explicit native launch mode, for example `--native-profile PATH`, plus a distinct create operation such as `--create-native-profile PATH`. Neither may select a default personal directory or retry another constructor after failure. Keep both existing fixture launch modes unchanged. Expose a small read-only profile-kind discriminator through the backend/Host for native form defaults; do not let the frontend select endpoint authority. General new-connection defaults should not silently embed dbunk_demo/15432 credentials. Save remains storage-only; Test and Connect remain separate intentional calls. The fixture-verification feature currently initializes in `main.rs` regardless of launch mode: reject `DBUNK_NATIVE_VERIFY` in general mode before initialization rather than permitting fixture automation under expanded endpoint authority.

No importer is needed to establish the fresh-profile capability. A later importer must create a destination through this constructor, validate a synthetic source read-only and use a consistent SQLite backup including WAL. Ordinary open must continue refusing unmarked legacy SQLite files.

## Two narrow prerequisites before arbitrary endpoints

**Probe cleanup deadline.** `test_development_connection` bounds `connect_tracked` to ten seconds, but success then awaits `connected.close()` and `tasks.drain()` without a deadline (`connections.rs:357–363`). `DedicatedConnection::close` awaits the driver join (`postgres/dedicated.rs:208`). A peer that stalls close can retain the credential/startup guards after the connection timeout has ended. Apply one absolute probe/cleanup deadline, abort owned drivers on expiry and drain them before completion, following the existing bounded native-reader cleanup pattern. Do not report Reachable before the owned probe settles; distinguish connection success from a persistent connected session. This is a source-level risk finding, not a reproduced failure.

**Form and stored-option bounds.** Existing form validation caps name/host/database/user at 256 bytes, refuses NUL/empty required fields and port zero, and caps role/search-path entries. Optional TLS path/server-name strings are copied without equivalent bounds in `into_stored`. General input needs explicit finite byte/NUL checks for these fields and validation on loaded metadata before admission. Save can validate structure without DNS, certificate-file reads or connectivity. Valid-looking but unreachable endpoints may be saved; Test/Connect must report typed failure and leave the document disconnected. No password, raw server error or certificate contents should enter diagnostics.

## Focused acceptance tests

- Fresh general create/open, in child processes where necessary: private canonical paths, independent IDs, exact marker/SQLite match, no Keychain adapter call before configuration. Reopen preserves IDs and credential namespace.
- Cross-mode refusal: general opener on stage03/stage04, fixture opener on general, missing/mixed marker, future/corrupt marker, mismatched path/database/UUID/namespace. Assert original bytes preserved and no credential/network admission. Existing fixture endpoint-substitution tests continue unchanged.
- Launch parsing keeps existing fixture flags intact, rejects mixed modes and general-mode `DBUNK_NATIVE_VERIFY`, selects profile-aware form defaults, and never falls back to another opener or a default directory after an error.
- Existing-directory creation refusal, symlink/hardlink/permissions refusal, concurrent lock refusal, same-process general-to-other-general and general-to-stage04 switching refusal. Test stage03 mixing only if that additional contract is implemented.
- Save/list/reopen an ordinary syntactically valid non-fixture PostgreSQL form with exact TLS/driver/policy metadata, using PlainSqlite and injected stores. Assert no connection attempt during save, settings/workspace reload or draft restoration. Restored query/table/tool documents remain disconnected, with acknowledged intent retained.
- Empty/NUL/oversize/port-zero form failures preserve the previous saved row and secret. Unsupported engine/SSH/options remain visible and inactive, never silently normalized to supported PG.
- Explicit Test uses the supplied unsaved form and scoped saved password semantics; only an explicit call reaches the connection edge. Use an owned mock protocol peer or injected connector for success, authentication/TLS/database/timeout failures and a hung close. Verify no Ready/connected state on failure and joined driver cleanup within the same absolute deadline.
- Explicit Connect admits the saved endpoint under the current capability, then respects current read-only/safe-mode policy. Concurrent save/delete/credential reset retires old tasks and cannot cross startup admission; stale documents refuse. Reuse existing admission barriers rather than inventing a second runtime.
- Injected Keychain namespace and rollback tests prove primary/backup accounts derive only from the general marker, never ordinary production or a fixture's namespace. Locked, wrong-passphrase, denied/missing and interrupted-recovery cases remain truthful and preserve recoverable state.

Useful existing test patterns: `backend/development/tests.rs` (child-process profile isolation, injected Keychain builder, identity/fixture refusal), `development/admission_tests.rs` (startup barriers and queued mutations), `development/connection_tests.rs` (connection journals and owned mock protocol peer), and native workspace persistence tests. No test or build was run for this reconnaissance. Live/package acceptance remains pending and must use separately named disposable targets.
