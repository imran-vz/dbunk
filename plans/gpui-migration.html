One measurement method for both hosts. In-app timers are not comparable: a WebView's performance.now() and a GPUI frame callback cover different spans. Measure from outside the process, with release builds on the same machine, display mode, window size and power state.

  • Input latency: inject synthetic key events and detect the first changed frame at the caret through screen capture. Report p50 and p95 over a fixed keystroke count. Capture resolution is one refresh interval; state it with the result.
  • Scrolling: inject synthetic scroll events and take frame pacing from the same capture stream.
  • Memory and idle: sum the footprint and CPU time of the whole process tree. Tauri's total includes the WebKit content, GPU and networking helper processes.
  • Startup: launch to first interactive frame, from the same capture.

What the migration removes. This is the case for the change apart from rendering speed.

  • The 177 command wrappers and the serialization on both sides of each call.
  • The response-ownership and acknowledgement handling that ADR-0030 added for Tauri's IPC path, including the per-platform page-load events it depends on.
  • Renderer-reload lifecycle: webview generations and owner replacement after a page load.
  • TypeScript mirrors of Rust types, such as the ADR-0011 frontend connection union that shadows the ADR-0010 stored enum.
  • At cutover, the JS toolchain and its gates: Vite, tsc, oxlint, oxfmt and Vitest.

One core, two temporary hosts

TEMPORARY

src-tauri/

Existing React UI and thin Tauri command adapters. Remains usable throughout extraction.

TARGET

crates/dbunk-desktop/

GPUI views, workspace models, native integrations and one owned Tokio runtime.

BOTH HOSTS CALL ↓

crates/dbunk-core/

Application services, engine adapters, session managers, persistence, credentials, safety gates and typed events. No GPUI or Tauri dependency.

Keep the boundary small. Expose domain operations such as opening a Query Session or applying a mutation. Move validation, connection resolution, authorization and audit out of command wrappers into those services. Keep drivers private. GPUI must not call lower-level operations that skip existing safety checks.

Own runtime and lifecycle explicitly. Each executable owns one Tokio runtime and supplies its handle to core services. GPUI stays on its UI thread. Database work, SSH, keyring operations, parsing and heavy file work run off that thread. Window/owner identity, focus, invalidation and shutdown become host-neutral inputs. Zed's tree carries an Apache-2.0 gpui_tokio crate; inspect it as a reference for the bridge.

Preserve streaming invariants, not the IPC protocol. The invariants are fixed: retained rows and event bytes stay bounded; cancellation and shutdown stay reachable when the consumer is slow or the queue is full; events from a stale generation or execution are rejected; each execution reports exactly one terminal outcome; partial results and notices survive; nothing is rerun silently after a reconnect. Sequence numbers, cumulative ACKs and the credit loop are the mechanism that holds those invariants across an asynchronous IPC boundary. The Tauri adapter keeps that mechanism unchanged during coexistence. The native host may use a bounded in-process sink instead, but only once the same failure-mode tests pass against it. Batch UI notifications instead of repainting per row.

Map lifecycle by cause. Owner replacement and webview generations exist because a renderer can reload. A native host has no reload, so the owner maps to a window or tab entity lifetime. ADR-0021 focus leases are about window focus and apply unchanged.

Choose one dependency path. Zed's editor and GPUI Kit resolve to different GPUI packages and cannot be assumed to share a binary. Decision 2 and the stage 01 spike choose between them. Use GPUI's entity model for frontend state on either path. Dependency paths below.

Mixing the paths is not a pinning task. Zed's editor depends on the package named gpui; GPUI Kit depends on the package named gpui-pre. Cargo treats those as unrelated crates, so their GPUI types do not unify, and a [patch] entry replaces a package with one of the same name. Combining Zed's editor with GPUI Kit's grid therefore most likely needs a maintained fork of one side. Confirm by compiling only if both paths survive decision 2.

Reading Zed without reusing it. Zed's workspace crate manages panes, docks, items and app state, and depends on project, client, remote, session and Node runtime infrastructure. Its ownership and item patterns remain a design reference on either path. Reading GPL source for design ideas is different from copying it; path K must not import or transcribe Zed's GPL code.

Frontend state on either path. A workspace entity coordinates query tabs, navigator and result-grid entities. Tabs hold editor handles and bounded result models; async callbacks use weak handles and existing generation checks. Database actors and transaction truth stay in dbunk-core.

Decisions and constraints

Editor and grid are the largest uncertainty

A generic native editor or table does not establish Monaco or dbunk grid parity. Completion context, SQL formatting, multicursor editing, specialized cells, FK drill-down and wide-table performance need explicit verification. Use the spike to choose reuse versus focused custom work.

Native rendering does not guarantee a faster application

The expected benefit is a native rendering path and fewer cross-language copies. SQL latency, retained data size and over-broad state updates still matter. Measure total CPU/GPU and memory rather than relying on framework performance claims.

Upstream tracking is a standing cost

Neither path offers a stable API. The inspected Zed revision was committed on 1 Oct 2026 and Zed publishes no editor crate; GPUI Kit pins exact snapshots because a looser requirement moved applications onto a snapshot it did not compile with. Each upgrade is a migration of its own, and skipping upgrades forfeits platform and accessibility fixes. Budget for it as recurring work, and treat a fork of either side as a larger version of the same cost.

Iteration gets slower

The current UI reloads in place through Vite. A native view change needs a Rust rebuild, and path Z compiles a large part of Zed. Agent-driven work also loses WebView preview and DOM inspection. Stage 01 measures the rebuild times; treat a slow loop as a cost against every later stage, not a one-off.

The WebView supplies behavior that has to be rebuilt

Selection and copy of any text, form controls, context menus, tooltips, focus order, drag and drop and the accessibility tree all arrive with the browser. Schema maps depend on React Flow, and neither path lists a node-graph component. Each is small alone; together they are a large share of the port and the easiest part to underestimate.

A moving baseline grows the rewrite

Every feature added to the React UI after the baseline is built again natively. Decision 3 exists to bound this. Without a rule, stage 06 has no fixed size.

Existing architectural decisions need narrow amendments

ADR-0007 names Tauri-managed storage startup; ADR-0011 describes the frontend connection union; ADR-0021 ties session ownership to the renderer/window; ADR-0030 includes webview-generation lifecycle. Amend these for native hosts while preserving their data, type and ownership invariants. Preserve ADR-0024 safety and ADR-0031 execution semantics.

macOS first is a release sequence
