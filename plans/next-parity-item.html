Raw UTF-8, retained allocations and escaped JSON have separate budgets. A 256 KiB field can expand beyond a 1 MiB page, so values are chunked. Runtime/allocator overhead is measured separately.

Implementation sequence

  1. Prove capture and deparser behavior

    Disposable PG16 interleaving fixtures for rename, drop and index changes. Establish lock/snapshot ordering or explicit not-comparable fields. Stop if the remaining comparison is not useful.

  2. Protocol + normalization + byte accounting

    Closed PG16 field checklist, counterpart inventory, immutable value references and UTF-8 chunks. Test worst-case JSON expansion and concurrent page requests.

  3. Bounded catalog capture

    Implement the proven capture sequence. Enforce PG16/PG16, permissions, complete inventory and definition limits.

  4. Deterministic structural diff

    Compare facts using portable identity. Preserve unsafe expressions as not comparable.

  5. Native jobs + typed client

    Start the deadline at admission, including credentials and tunnels. Reconcile uncertain starts and fence both endpoints through cleanup.

  6. Failure + boundedness validation

    Disposable PostgreSQL fixtures, concurrent DDL, TLS, cancellation, cap boundaries and memory measurements.

  7. Backend handoff

    Required checks, contract tests and accurate progress docs. Then plan the UI with several static alternatives.

Decisions that prevent misleading results

No automatic semantic SQL rewriting

Map structured schema references only. Never replace schema names inside literals or deparsed expressions. OIDs are local lookup keys, not cross-database identity. Same named custom types do not prove equal type definitions.

No global snapshot promise

A repeatable-read transaction alone does not prove deparser consistency. Step 1 must handle successful mixed-metadata reads, including rename races. Unproven fields become not comparable; failed required capture aborts.

Read-only is not a server-code sandbox

The comparator never executes captured expressions as SQL, scans user rows or issues DDL/DML. Metadata rendering can invoke installed type output or access-method support code. The fixture must verify this boundary.

Excluded does not mean absent

Inventory relation names and kinds before filtering. An ordinary source table and a same-named target view or partitioned table produce an excluded-counterpart result, never a missing-table claim.
